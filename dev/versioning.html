构建与归档文档¶

本地构建不会部署站点，也不会启用 GitHub Pages。站点根页经 latest/ 跳到最新已就绪的发布版；尚无已就绪发布版时，根页打开 versions/，不生成 latest/。全部版本入口为 versions/，开发版位于 dev/，发布版位于固定 tag 的同名目录。

本地检查¶

按贡献指南准备文档开发环境，在源码根目录运行：

python run_docs.py --output-dir output_data/docs-preview

输出目录必须为空。命令严格构建 HTML、执行教程与 README 示例，再核对 API 地址、知识目录和内部链接。 教程与 README 的执行组从准备后的文档源枚举，再核对实际执行报告；README 首例及排盘、流运、查知识、判据求值、编辑每项至少须有一个可执行代表例。 API 示例从源码的 docstring 与属性说明发现，先与实际页面核对，再各自在独立进程运行并校验断言或紧随的输出，每例限时 30 秒。 BaziPrecision 的 Examples 是出生精度的文字对照，不计作可执行示例。全部成功后才交付成品。打开 output_data/docs-preview/html/index.html 查看。

Python 版本政策、运行时检查和完整门禁统一见贡献指南。 临时目录遵循 Python 的标准 TMPDIR 等环境设置。

run_docs.py --version vX.Y.Z 只接受干净检出且当前提交恰为该 tag 的源码；不接受把开发源码标成任意版本。开发版也记录实际提交和工作树状态，含未提交修改的构建不能进入归档。

新构建在 build.json 的 built 字段记录实际 UTC 构建时间（YYYY-MM-DDTHH:MM:SSZ），版本信息页显示同一时间。版本列表先列最新已就绪发布版，开发版排最后，显示构建时间与源码提交；旧构建未记录时间时明确标为“构建日期未记录”，不以提交日期代替。

维护者手动归档¶

Publish Documentation 工作流只有手动入口，默认模式 rehearsal 只构建，不写归档或部署。写入与部署只允许主仓的 main 分支执行；PR 和普通 push 不会触发它，fork 也不满足写入和部署条件。

milestone/<版本> 集成分支可手动选择 version=dev、mode=rehearsal 检查本次触发提交的文档。 这些构建不更新线上 dev/；归档与部署须等汇总 PR 合入 main 后另行执行。

模式

做什么

rehearsal

检出并检查选定源码；选发布 tag 时也构建本次触发提交的 dev，上传短期工件，不修改站点

publish

归档本次构建并部署完整站点，随后回读；不直接改成 ready

promote

全站回读通过后将选定版本标为 ready；选发布版时也提升同一归档提交的 dev（如有），更新入口

resume

验证持久归档后原字节重新部署，不改任何文件

工作流要求已有 docs-site 归档分支。分支缺失时停止，按下文“手工重建归档分支”恢复后再运行。

归档分支持久保存静态文件，不以短期 Actions 工件代替多版本保留。发布版目录已有内容时拒绝异字节覆盖；dev/ 可整目录更新。后续发布只追加本版并保留旧版原字节，不重建旧 tag。

选择发布 tag 执行 publish 时，同次运行先构建该 tag，再构建触发运行的固定源码提交（github.sha）作为 dev；两份候选由同一个工件 ID 传递，一次归档提交同时保存两版。即使补发符合下段前提的旧 tag，dev 也不取旧 tag 的源码。选 dev 时只更新开发版；promote 和 resume 不重建源码。

发布版构建还要求该 tag 已有正式 GitHub Release，并携带身份一致的 release.json；仅能归档自身带有文档构建器的版本，不修改旧 tag 来补文档。文档发布失败不表示软件尚未发布，archived 在版本列表中显示为“文档待就绪”。

archived 已归档，尚未通过线上回读；ready 已通过线上回读，选择页才提供链接。

维护者确认平台前提后，通常先 publish，等自动回读完成，再运行 promote。全站回读逐文件核对同一归档提交，并分别计算各版摘要；提升发布版与 dev 使用各自摘要，归档分支在回读后指向了其他提交就须重新核对。新内容归档后先为 archived，通过回读和提升后才为 ready。

latest 只指向已回读的 ready 发布版；开发版不参与。归档已成功、但部署或回读失败时用 resume 重试；需要补归档时才重跑 publish。最新工具只接受完整的当前入口布局，拒绝旧布局及含 pending 状态的清单；旧快照的恢复见下节。

手工重建归档分支¶

分支重建是一次性维护操作，不在发布工作流中自动执行。

  1. 确认 docs-site 确实缺失，而不是查询或权限失败；暂停可能更新该分支的运行。保全可信归档提交或静态备份，记录提交身份、文件清单与摘要。

  2. 在独立目录恢复历史版本目录的原字节，包括隐藏文件与各版 build.json。不要重新构建旧 tag 来冒充原归档；没有可信静态备份的版本须明确列为无法保证恢复。

  3. 旧布局先用生成该归档时的历史工具读取和核验。归档提交正文中的 Workflow run 编号可用于定位那次 Actions 运行； 从该运行的源码提交（github.sha）检出 run_docs_site.py 及其依赖，发布工作流从这一提交的 control/ 目录运行工具。 各版 build.json.commit 标识文档的构建源码，不一定是归档工具版本；手工备份须另有工具版本记录。 核验后整理成当前的 archived／ready 记录。旧 pending 条目没有目录，不能直接改成已归档版本，也不能带入新清单。 保留已有版本的源码提交、目录摘要与回读状态；有静态字节但没有可信回读记录的版本用 archived。

  4. 用当前 run_docs_site.render_site 根据这些记录与原目录文件生成完整站点，入口文件一起生成，不混搭新旧模板。完全没有可恢复版本时，render_site({}) 可生成空站点骨架：index.html、versions.json 与 versions/index.html；根页跳转版本列表。

  5. 用 run_docs_site.load_archive 核对完整站点的清单、构建身份、目录摘要与当前入口，并与备份逐文件对照历史目录。确认拟提交的 Git tree 全部为 100644 普通文件，tar 导出与 Git tree 一致；旧 build.json 可以没有 built，不要补写猜测的时间。

  6. 通过维护者批准的签名提交流程建立 docs-site，核对实际父提交、完整树和签名。不关闭分支保护，不覆盖维护期间其他人新建的分支。

  7. 有现存版本时，选择其标签运行 resume，全站回读通过后再按需 promote 尚为 archived 的版本。若只有空骨架，先 publish；不存在的标签不能用于 resume。

平台前提与失败边界¶

首次实际使用前，维护者须另行将 Pages Source 设为 GitHub Actions，并检查 github-pages 环境、归档分支规则及默认令牌的权限。构建、归档和 Pages 部署分 job 授权，不新增个人令牌或签名密钥。签名、父提交、树、身份或回读字节不符时停止，不通过关闭保护来绕过。

归档提交已生效但响应丢失时，可从归档继续重试。临时分支清理失败或运行取消可能留下 docs-site-staging-*，确认对应运行已经结束后由维护者检查清理。

本地测试和模拟响应不能替代 GitHub 实际运行。默认令牌、规则集、工件重跑、特殊文件模式及 CDN 可见性仍需首次部署后的回读验证；在这之前不宣称站点已经上线。
