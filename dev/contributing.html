贡献指南¶

本库既是八字排盘库，也记录作者整理的八字知识。欢迎以 issue 提交勘误和出处补充；PR 先开 issue 讨论，讨论通过后才接受。

先开 issue¶

想做的事

怎么提

更正某条知识，或为它补出处

用“知识勘误与出处补充”模板

提出另一流派的读法

用“流派读法提案”模板

报告程序的可复现问题

开普通 issue，写明 Python 版本、最小代码和实际与预期结果

改代码、文档或工具

开普通 issue 说明问题与方案，维护者回复同意后再写 PR

先在文档站选择版本，再进入“知识目录 → 条目”查找 ID，也可直接贴所读条目的页面链接。 找不到 ID 时，描述原文及问题即可，不必下载 JSON。

没有 issue 讨论的 PR 不会合并。讨论通过只表示接受这个方向，PR 仍须通过下文的门禁与审阅。

出处要求¶

本库不收没有出处的规则。提交规则勘误或流派读法时，请提供可核对的原文：

  • 作品、署名、版本：古籍写书名、作者或注者、所用版本（刻本、影印本、点校本或电子书的出版信息）。

  • 位置：页码、卷次或章节；有在线原文时给出所用版本的链接，不用搜索结果或转载摘要代替原文。

  • 摘录：原文逐字摘出，保留原有字词、标点与异体字，不改写、不规范化。

  • 能支持什么、不能支持什么：一句话写清这段原文支持哪条结论，以及它没有说什么。

流派之间说法不同时，各读法分别记录并分别写出处，本库不合成一个“正确”规则。

模板收集的是线索，不是可直接导入的 JSON。填写与整理时：

  • 没有在线链接，也可先提交纸本作品、版本、位置和摘录，在表单指定的位置列出缺项。

  • 正式来源记录只必填 source_id 和 work，其余信息按材料填写。能加载不等于通过知识审核， 不为填满字段而编造链接或占位值。

  • 摘录属于白文正文、夹注还是原创说明，写入 limitations，保留它对读法的限制。

  • 表单中的 attribution 是来源署名，条目署名由维护者另行填写。

来源状态的含义¶

来源记录可用 state 表示核验状态。与出处核对直接相关的两种状态是：

  • witnessed：原文出处已经核定，有可核对的作品、版本、位置和摘录。

  • unverified：来源尚未核实。

未填状态不表示已核实。两个来源不自动构成独立见证，作品与版本是否同源须由维护者核对； 加载器不检查来源数量或收录政策。条目保留自己的前提、读法、署名和限度， 各字段含义见知识库指南，字段定义与校验见 knowledge.py。

提 PR 之前¶

默认从 main 开分支并向 main 提 PR。采用 milestone/<版本> 集成分支的阶段任务， 从指定集成分支开施工分支，阶段 PR 以该集成分支为目标；例如 v3.0.0 使用 milestone/v3.0.0。 一个 PR 只做 issue 中讨论过的事，逐张审阅合并后再开始下一张。

阶段 PR 正文写 Part of #<issue>。阶段工作完成后，从集成分支向 main 提汇总 PR， 只对已完成验收的代码任务写 Closes #<issue>，并使用 merge commit 保留阶段历史。 来源收藏、真实发行等独立验收任务，在实际完成后关单。

main 与 milestone/** 的 PR 都运行完整 CI 和 PyPy 检查，合并后的 push 运行快速检查。 维护者另行配置并回读分支保护：必需检查须对应实际 CI job 名，禁止强推和删除； 修改工作流不会自动启用这些设置。正式发布仍从 main 执行，见发布说明。

知识编辑来源是 bazi/knowledge_data.json，不是生成的目录页面。 内容保护测试将每个对象、来源和条目分别与 tests/data/knowledge_content.json 的指纹比较。 有意修改知识后，先核对文字及出处，再只更新受影响记录的指纹，不重建整份基准。 计算式为 sha256(json.dumps(asdict(record), ensure_ascii=False, sort_keys=True).encode('utf-8')).hexdigest()； record 是 KnowledgeBase.load() 中对应的记录，三个函数分别来自 hashlib、json 和 dataclasses。

维护规则与知识关联时：

  • 计算表归 rules.py，默认及合法配置归 school.py，知识文字、来源和状态归知识注册表；共表和派生关系继续从计算定义取值。

  • 新读法另加定义，保留既有定义；新增神煞的表值、锚点与查找位置分别核定其自身出处，不沿用其他神煞的设置作默认。

  • 变更时核对条目 ID、定义成员、表值、锚点和实际查找位置；知识条目与计算表分别维护， 同一读法的内容应相符。

  • 原文、解释、锚点依据及来源限度分别保留；不把转载网站当成独立来源，也不因建立关联而升级来源状态。

  • 覆盖表的属性／字段集合与示例由文档检查核对；这些检查不裁定命理依据，也不证明表外规则穷尽。

准备环境¶

本库及其运行时检查支持 Python 3.11+；构建文档、检查文档工具及运行完整门禁需要 Python 3.13+。PR CI 在 3.11 和 3.12 上检查运行时，在 3.13 和 3.14 上运行包含文档的完整门禁，另有跨平台和 PyPy 兼容检查。本机一次运行不等于全部 CI 通过。

使用 Python 3.13+，在仓库根目录创建独立开发环境：

python -m venv .venv

macOS／Linux 用 source .venv/bin/activate 激活；Windows PowerShell 用 .\.venv\Scripts\Activate.ps1。激活后安装：

python -m pip install -r Requirements.txt
python -m pip install -r docs/requirements.txt
python -m pip install celestial-calendar==0.6.1

Requirements.txt 是开发依赖，docs/requirements.txt 是文档工具依赖，两者都不是运行时依赖；celestial-calendar==0.6.1 是历法测试用的工具依赖。

如果在 Python 3.11／3.12 上检查运行时，另建对应版本的环境，只安装 Requirements.txt 与 celestial-calendar==0.6.1，使用 python run_tests.py -a -v --runtime-only。它保留库测试、覆盖率、lint、运行时类型检查、安装工件与安装命令检查；tests/test_docs_site.py、tests/test_docs_workflows.py 仍会收集。类型检查排除 docs/、tests/docs/、run_docs.py 和 run_doc_checks.py，测试不收集 tests/docs/，也不构建文档。文档完整检查仍在 3.13+ 环境中执行；不要尝试在 3.11／3.12 环境安装新版 Sphinx。

生成后的 HTML 是静态文件，读者只需浏览器；阅读文档或在 Python 3.11 中运行其中的库调用示例，不需要安装文档工具。

完整门禁¶

PR 前须在上述 Python 3.13+ 开发环境、仓库根目录实跑完整 CPython 门禁：

python run_tests.py -a -v

完整检查包含全部测试与 100% 覆盖率检查、ruff check、mypy、python -O 输入契约检查、安装工件及真实安装命令验证，以及文档构建与检查。CLI 专项测试计入库覆盖率，不另设旧脚本冒烟任务。

  • 裸 python run_tests.py 不含 slow、hkodata 测试和可选任务，不能代替完整门禁。

  • 工件验证可能联网下载构建与类型工具；安装命令的导出测试在仓外临时目录运行。

  • 只改知识 JSON 或文档也要跑完整门禁。

  • 不要运行 ruff format 或其他自动格式化器，代码保留两空格缩进和纵向对齐。

只构建并检查文档¶

在上面的 Python 3.13+ 开发环境中运行：

python run_docs.py --output-dir output_data/docs-preview

输出目录须为空。命令严格构建 HTML、执行 README 与教程示例，再检查 API 地址、完整知识目录、 内部链接及发布／迁移页面；成功后可用浏览器打开 output_data/docs-preview/html/index.html。 已经生成的 HTML 阅读不需要 Python。此命令不部署站点、不启用 Pages，构建与归档政策见 文档归档说明。

要保留已验证的安装工件，见本地保留已验证工件； 不要把一次源码测试通过当作另一份 wheel 已被测试。

历法数据维护¶

离线重建工具为 HKO 编码器和根目录的 天文表生成器 run_calendar_generation.py，天文表的记录布局见 数据格式。 源码与 sdist 保留生成器、tests/calendar/hko_data/ 下的 HKO 原件、编码表及编解码工具， 供重建数据与独立对拍；这些材料不进入 wheel，也不是公开 Python API。 wheel 只带运行时需要的代码与数据，安装包缺表时应重装包，不运行生成器修补。

提交与 PR 正文¶

  • 提交须签名，由维护者核验。提交信息不要带 Co-Authored-By:。

  • PR 正文用中文，分四节：

    1. 内容：改了什么、为什么；

    2. 测试：新增或调整了哪些测试；

    3. 验证：运行的命令与结果，如 python run_tests.py -a -v 的退出码；

    4. 范围说明：没做什么，以及相关 issue 编号。

  • 正文末尾写归属，用实际贡献者的 GitHub 账号和实际使用的工具与型号，不要写会话链接。使用 AI 工具时：

    Built by @<你的 GitHub 账号> with <工具名> (<型号>).

    用了多个工具，用 and 连接；没有使用 AI 工具，写 Built by @<你的 GitHub 账号>.。

  • 不写本机路径、主机名等个人信息；示例命盘须匿名，用化名，出生地降到省级。

代码与知识的约定¶

  • 领域术语用拼音，如 Tiangan、Shensha；JSON 中的干支、十神等领域值用中文，性别保存为 male／female，配置和键沿用既有拼写。

  • 自有 API 与源码说明以中文为主，引文保留来源原有的字词和标点。

  • 改知识即改规则：新增或修改条目前，须先在 issue 中让维护者核定出处与口径。

审阅与合并¶

维护者负责安排独立的正确性与设计审阅，以及修复后的复验。外部贡献者无需自行安排独立审阅或购买工具订阅。 仓级编码与执行约定见当前主干的 AGENTS.md，该链接用于查看现行贡献政策。 合并由维护者决定。普通与阶段 PR 可选择 squash；集成分支汇总到 main 时使用 merge commit。
